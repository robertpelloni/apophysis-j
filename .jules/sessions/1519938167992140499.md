# Project Architecture & Patterns (Apophysis-j)

## 1. Core Purpose and UI Framework
*   **The Goal:** `apophysis-j` is a Java port of the legendary Windows fractal flame editor, Apophysis. It is intended to run on any machine with Java 1.8+ and bring fractal flame creation to Mac and Linux.
*   **Thinlet UI:** The project uses a custom, aging UI framework called **Thinlet** (`com.thinlet.Thinlet`). This framework is implemented as a massive, monolithic class (over 7,000 lines of code) that manually handles AWT/Swing bridging, event dispatching, layout bounds calculations, scroll behaviors, and rendering. It parses XML descriptors and dynamically binds UI events to method calls via reflection.

## 2. Rendering and Extensibility
*   **Flam3 Integration:** The backend logic relies heavily on `flam3` (Scott Draves' original algorithm). Apophysis-j bridges its logic out to native executions or scripts. For example, rendering and exports often execute external processes (historically via `Runtime.exec`, now modernized to `ProcessBuilder`) calling native `flam3` binaries.
*   **Plugin Architecture (`XForm.java`):** The application has a robust plugin architecture. It dynamically scans the `plugins/` directory for `.jar` files and uses a `URLClassLoader` to instantiate implementations of the `Variation` class via reflection. This allows fractal artists to add custom mathematical variations without recompiling the main application.

## 3. Scripting Engine
*   **Rhino Integration:** The application exposes a scripting API to automate fractal generation, mutation, and batch rendering. It relies on Mozilla's **Rhino** engine (`rhino.jar`), bundled and managed via Ant dependency pulls. 

## 4. Modernization Efforts
The repository has been undergoing significant cleanup to conform to modern Java environments (moving past Java Applet constraints). Recent structural shifts include:
*   **AWT/Swing Deprecations:** Migrating legacy input masks (`InputEvent.ALT_MASK`) and modifier text retrievals (`getModifiers`) to their modern equivalents (`ALT_DOWN_MASK`, `getModifiersExText`).
*   **Applet Removal:** The `AppletLauncher.java` class was removed entirely since `java.applet.Applet` is defunct.
*   **Security Manager Fixes:** Legacy `AccessController.doPrivileged()` blocks have been removed in favor of standard `URLClassLoader` instantiations, aligning with the deprecation of the Java Security Manager in recent JDKs.
*   **Thinlet Bug Fixes:** We manually fixed `Thinlet.java` to support tooltip rendering over specific datatypes (trees, lists, tables) and solved scrollbar calculation bugs by checking explicit "scrollable" booleans.

## 5. Build and Ecosystem Governance
*   **Build System:** The project is compiled using **Ant** (`build.xml`). `ant build` compiles the main jar, the plugins jar, and copies resources. 
*   **Documentation Rigor:** Per the "Omni-Workspace Root" directive, the repository maintains strict global documentation. Files like `VERSION.md`, `CHANGELOG.md`, `ROADMAP.md`, `TODO.md`, `MEMORY.md`, and `HANDOFF.md` are dynamically updated. Versioning is central (currently `2.10.3`).

## 2. Rendering and Extensibility
*   **Flam3 Integration:** The backend logic relies heavily on `flam3` (Scott Draves' original algorithm). Apophysis-j bridges its logic out to native executions or scripts. For example, rendering and exports often execute external processes (historically via `Runtime.exec`, now modernized to `ProcessBuilder`) calling native `flam3` binaries.
*   **Plugin Architecture (`XForm.java`):** The application has a robust plugin architecture. It dynamically scans the `plugins/` directory for `.jar` files and uses a `URLClassLoader` to instantiate implementations of the `Variation` class via reflection. This allows fractal artists to add custom mathematical variations without recompiling the main application.

## 3. Scripting Engine
*   **Rhino Integration:** The application exposes a scripting API to automate fractal generation, mutation, and batch rendering. It relies on Mozilla's **Rhino** engine (`rhino.jar`), originally pulled via Ant script downloading `rhino-1.9.1.jar` from Maven Central. ## 4. Modernization Efforts
The repository has been undergoing significant cleanup to conform to modern Java environments (moving past Java Applet constraints). Recent structural shifts include:
*   **AWT/Swing Deprecations:** Migrating legacy input masks (`InputEvent.ALT_MASK`) and modifier text retrievals (`getModifiers`) to their modern equivalents (`ALT_DOWN_MASK`, `getModifiersExText`).
*   **Applet Removal:** The `AppletLauncher.java` class was removed entirely since `java.applet.Applet` is defunct.

# Project Architecture & Patterns (Apophysis-j)

## 1. Core Purpose and Domain
*   **The Goal:** `apophysis-j` is a Java port of the legendary Windows fractal flame editor, Apophysis. It brings fractal flame creation, manipulation, and rendering to Mac and Linux platforms. The project is configured to run on Java 1.8+.
*   **Omni-Workspace Context:** This repository operates under strict "Omni-Workspace Root" directives, meaning it is part of a larger ecosystem of submodules and requires rigorous documentation governance, continuous autonomous execution, and clean git history management.

## 2. UI Framework (Thinlet)
*   **Custom Framework:** The project uses an aging, XML-driven UI framework called **Thinlet** (`com.thinlet.Thinlet`). 
*   **Monolithic Design:** The UI engine is largely implemented as a massive, monolithic class (over 7,000 lines of code) that manually handles AWT/Swing bridging, event dispatching, layout bounds calculations, scroll behaviors, and rendering.
*   **Reflection-based Binding:** It parses XML UI descriptors and dynamically binds UI events to method calls via Java reflection.
*   **Recent Enhancements:** We recently patched native Thinlet bugs, specifically adding tooltip rendering support for complex datatypes (trees, lists, tables), resolving scrollbar calculation bounds based on explicit "scrollable" attributes, and ensuring tooltips cleanly hide during mouse wheel scroll events.

## 3. Rendering and Extensibility
*   **Flam3 Integration:** The backend rendering logic relies heavily on the `flam3` mathematical algorithm (created by Scott Draves). Apophysis-j bridges its internal logic out to native executions or batch scripts, invoking native `flam3` binaries for final rendering and exports.
*   **Plugin Architecture (`XForm.java`):** The application features a robust mathematical plugin architecture. It uses a `URLClassLoader` to dynamically load `.jar` files and instantiate implementations of the `Variation` class via reflection. This allows fractal artists to add custom formulas and mathematical variations without recompiling the core application.

## 4. Scripting Engine
*   **Rhino Integration:** The application exposes a Javascript API to automate fractal generation, mutation, and batch rendering. It relies on Mozilla's **Rhino** engine, which has been modernized to pull cleanly from Maven Central (version `1.7.14`).

## 5. Codebase Modernization Efforts
The repository has undergone significant refactoring to shed legacy technical debt and conform to modern Java environments:
*   **AWT/Swing Deprecations:** Migrated legacy input masks (e.g., `InputEvent.ALT_MASK`) and modifier text retrievals (`getModifiers()`) to their modern equivalents (`ALT_DOWN_MASK`, `getModifiersExText()`).
*   **Applet Removal:** The `AppletLauncher.java` class was removed entirely since `java.applet.Applet` is defunct in modern Java.
*   **Security Manager Fixes:** Legacy `AccessController.doPrivileged()` blocks have been removed in favor of standard `URLClassLoader` instantiations, aligning with the deprecation of the Java Security Manager in recent JDKs.
*   **Process Execution:** Replaced legacy `Runtime.exec()` invocations with robust `ProcessBuilder` patterns for external command execution.
*   **Constructors:** Replaced deprecated `Class.newInstance()` and `new Boolean()` calls with `.getDeclaredConstructor().newInstance()` and `Boolean.valueOf()` respectively.

## 6. Build System and Testing
*   **Build System Transition (Maven):** The project was historically compiled using **Ant** (`build.xml`). It has now been transitioned to use **Maven** (`pom.xml`) to better align with modern CI/CD patterns and robust dependency resolution. 
*   **Directory Structure Preservation:** To prevent massive git history disruption, the Maven `pom.xml` was explicitly configured to compile from the legacy `src/` directory layout rather than forcing a move to `src/main/java`.
*   **Unit Testing Setup:** Initialized a comprehensive testing suite using **JUnit 4**, configuring the Maven test source directory to `src/test/java` and creating the foundational `GlobalTest.java` to test core engine dependencies.

## 7. Documentation and Versioning Governance
*   **Strict Documentation Requirements:** The repository maintains continuous, global documentation. Files like `VERSION.md`, `CHANGELOG.md`, `ROADMAP.md`, `TODO.md`, `MEMORY.md`, `VISION.md`, `IDEAS.md`, `DEPLOY.md`, and `HANDOFF.md` are centrally managed and dynamically updated after every significant feature shift.
*   **Versioning Protocol:** The application adheres to a single source of truth for versioning found in `docs/VERSION.md` (currently `2.10.6`). Version bumps are systematically propagated to the changelog, the Maven `pom.xml` manifest, and commit messages.

# Project Architecture & Patterns (Apophysis-j)

## 1. Core Purpose and Domain
*   **The Goal:** `apophysis-j` is a Java port of the legendary Windows fractal flame editor, Apophysis. It brings fractal flame creation, manipulation, and rendering to Mac and Linux platforms. The project is configured to run on Java 1.8+.
*   **Omni-Workspace Context:** This repository operates under strict "Omni-Workspace Root" directives, meaning it is part of a larger ecosystem of submodules and requires rigorous documentation governance, continuous autonomous execution, and clean git history management.

## 2. UI Framework (Thinlet)
*   **Custom Framework:** The project uses an aging, XML-driven UI framework called **Thinlet** (`com.thinlet.Thinlet`). 
*   **Monolithic Design:** The UI engine is largely implemented as a massive, monolithic class (over 7,000 lines of code) that manually handles AWT/Swing bridging, event dispatching, layout bounds calculations, scroll behaviors, and rendering.
*   **Reflection-based Binding:** It parses XML UI descriptors and dynamically binds UI events to method calls via Java reflection.
*   **Recent Enhancements:** We recently patched native Thinlet bugs, specifically adding tooltip rendering support for complex datatypes (trees, lists, tables), resolving scrollbar calculation bounds based on explicit "scrollable" attributes, and ensuring tooltips cleanly hide during mouse wheel scroll events.

## 3. Rendering and Extensibility
*   **Flam3 Integration:** The backend rendering logic relies heavily on the `flam3` mathematical algorithm (created by Scott Draves). Apophysis-j bridges its internal logic out to native executions or batch scripts, invoking native `flam3` binaries via `ProcessBuilder` for final rendering and exports.
*   **Headless Feasibility:** A recent architectural review revealed that migrating to a pure headless Java renderer without native `flam3` binaries is a significant undertaking. The core `Renderer` class and its `ThreadTarget` interfaces are tightly coupled with the `Thinlet` GUI roots, requiring substantial decoupling before headless scaling can be achieved. We have begun decoupling this by successfully mocking `ThreadTarget` interfaces inside JUnit tests.
*   **Plugin Architecture (`XForm.java` & `Variation.java`):** The application features a robust mathematical plugin architecture. It uses a `URLClassLoader` to dynamically load `.jar` files and instantiate implementations of the `Variation` class via reflection. `Variation.java` forms the core mathematical blueprint that specific plugins (e.g. `BlobVariation`, `LinearVariation`) implement to apply geometry mutations.

## 4. Scripting Engine
*   **Rhino Integration:** The application exposes a Javascript API to automate fractal generation, mutation, and batch rendering. It relies on Mozilla's **Rhino** engine, which has been modernized to pull cleanly from Maven Central (version `1.7.14`).

## 5. Codebase Modernization Efforts
The repository has undergone significant refactoring to shed legacy technical debt and conform to modern Java environments:
*   **AWT/Swing Deprecations:** Migrated legacy input masks (e.g., `InputEvent.ALT_MASK`) and modifier text retrievals (`getModifiers()`) to their modern equivalents (`ALT_DOWN_MASK`, `getModifiersExText()`).
*   **Applet Removal:** The `AppletLauncher.java` class was removed entirely since `java.applet.Applet` is defunct in modern Java.
*   **Security Manager Fixes:** Legacy `AccessController.doPrivileged()` blocks have been removed in favor of standard `URLClassLoader` instantiations, aligning with the deprecation of the Java Security Manager in recent JDKs.
*   **Process Execution:** Replaced legacy `Runtime.exec()` invocations with robust `ProcessBuilder` patterns for external command execution.
*   **Constructors:** Replaced deprecated `Class.newInstance()` and `new Boolean()` calls with `.getDeclaredConstructor().newInstance()` and `Boolean.valueOf()` respectively.

## 6. Build System, Testing, and CI/CD
*   **Build System Transition (Maven):** The project was historically compiled using **Ant** (`build.xml`). It has now been transitioned to use **Maven** (`pom.xml`) to better align with modern CI/CD patterns and robust dependency resolution. 
*   **Directory Structure Preservation:** To prevent massive git history disruption, the Maven `pom.xml` was explicitly configured to compile from the legacy `src/` directory layout for the main sources rather than forcing a move to `src/main/java`.
*   **Unit Testing Setup:** Initialized a comprehensive testing suite using **JUnit 4**. The Maven configuration correctly delineates `src/test/java/` for test sources. Foundational tests (`GlobalTest.java`, `ScriptConverterTest.java`, `TriangleTest.java`, `PivotTest.java`, `RendererTest.java`) ensure core engine dependencies, mathematical geometry, text-formatting, and dummy rendering thread isolation execute correctly.
*   **Automated CI/CD:** A GitHub Actions workflow (`.github/workflows/maven.yml`) has been established to automatically trigger `mvn -B package` on pushes and pull requests against the `master` branch.

## 7. Documentation and Versioning Governance
*   **Strict Documentation Requirements:** The repository maintains continuous, global documentation. Files like `VERSION.md`, `CHANGELOG.md`, `ROADMAP.md`, `TODO.md`, `MEMORY.md`, `VISION.md`, `IDEAS.md`, `DEPLOY.md`, and `HANDOFF.md` are centrally managed and dynamically updated after every significant feature shift.
*   **Versioning Protocol:** The application adheres to a single source of truth for versioning found in `docs/VERSION.md` (currently `2.10.11`). Version bumps are systematically propagated to the changelog, the Maven `pom.xml` manifest, and commit messages.
